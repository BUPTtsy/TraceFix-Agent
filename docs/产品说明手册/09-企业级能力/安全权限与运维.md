# 企业级能力：安全、权限与运维

「企业级 & 用户级可用」的标准拆成两部分：**用户级**（个人开发者装上就能用、出错能自助排查）和**企业级**（多人协作、权限隔离、合规、稳定运行）。

## 1. 现状

## 2. 目标设计 📐

### 2.1 身份认证

| 形态 | 方式 |
|---|---|
| 个人模式 | 默认只监听 loopback，可免登录；可选本地密码 |
| 团队 / 企业 | OIDC SSO（Keycloak / Azure AD / 飞书 / 钉钉）、GitHub OAuth |
| CLI / 自动化 | OAuth 设备码登录；API Token（有范围、有期限、可吊销、只显示一次） |
| GitHub 集成 | 安装在公司 github.com 组织上的 GitHub App；凭据由部署统一管理，只发往 github.com / api.github.com；内网经出口代理访问；PR 中不上传内部产物（见 `02-仓库交付流水线/GitHub接入与合并请求.md`） |

### 2.3 多租户隔离

- 所有业务表都带 `org_id`，并启用 Postgres Row-Level Security，由会话变量 `app.org_id` 控制可见范围。
- 对象存储按 `org/<id>/` 分前缀；每个组织使用独立的数据加密密钥（KMS 信封加密）。
- Worker 按组织打标签，企业客户可以使用专属的 Worker 池。
- 沙箱和浏览器容器不跨组织复用。

### 2.4 审计

- 结构化审计记录：`{id, at, actor, actor_type(user|token|system), org, project, action, target, before, after, ip, user_agent, request_id, result}`。
- 只允许追加，并用哈希链（每条记录包含上一条的哈希）防篡改；支持按时间范围导出。
- 覆盖范围：登录、权限变更、Profile 命令变更、规则发布、审批、发布、数据导出、reasoning 查看。

### 2.5 密钥与敏感数据

- 密钥统一放在 Vault / KMS；Worker 用短期凭据按需拉取。
- 测试账号使用占位符机制（见 `03-Agent运行时/浏览器MCP接入.md` 2.4 节），明文不会出现在模型上下文和轨迹中。
- 脱敏升级：在现有正则规则基础上，加上「已注入密钥的精确值反查」（每个 Run 维护已注入值集合），以及截图 OCR 遮盖。
- 仓库与 CI 中接入 secret scanning（例如 gitleaks）。

### 2.6 沙箱加固（企业选项）

- 容器运行时可选 gVisor / Kata，提供更强的内核隔离。
- K8s 部署：每个 Run 一个 Pod，NetworkPolicy 默认拒绝出站，只放行被测应用和浏览器之间的流量。
- 镜像按 digest 锁定并做 cosign 签名校验；生成 SBOM；定期扫描漏洞。
- 构建网络只放行包镜像源白名单（npm registry 镜像）。

### 2.7 可观测性

| 类型 | 内容 |
|---|---|
| Tracing | OpenTelemetry：Job → Run → Step → 模型调用 / 工具调用，形成层级 span；trace id 写入事件和日志 |
| Metrics | Run 成功率（按结果分类）、死循环异常率与各类循环信号的触发次数、各阶段耗时、模型延迟 / 错误率 / 429 次数、token 用量、队列深度、沙箱数量、浏览器 MCP 断线次数 |
| 日志 | JSON 结构化日志，带 request_id / run_id，经过脱敏 |
| 看板与告警 | Grafana 看板；告警条件：成功率骤降、死循环异常率升高、队列积压、用量异常偏高、孤儿容器。告警只通知，不会暂停或结束 Run |

### 2.8 可靠性与 SLO

| 项 | 设计 |
|---|---|
| 队列 | Postgres `SKIP LOCKED` 队列（少一个组件依赖）；规模大时换 Redis Streams |
| Worker | 心跳 15 秒；超时由其他 Worker 从 checkpoint 接管 |
| 并发控制 | 同一仓库 + 同一分支的发布串行执行（advisory lock）；Run 级锁跨进程生效 |
| 备份 | Postgres PITR；对象存储启用版本控制；每季度做一次恢复演练 |
| 升级 | schema 迁移用 Alembic；事件 / 轨迹 schema 带版本号，可向后读取 |

| SLO | 目标 |
|---|---|
| 控制面 API 可用性 | 99.9% |
| 事件推送延迟（产生 → Web 可见） | P95 ≤ 2 秒 |
| 任务启动延迟（排队 → PREPARE 开始） | P95 ≤ 60 秒（有空闲 Worker 时） |
| 因基础设施故障进入 PAUSED 的 Run 比例 | ≤ 3% |
| 死循环异常率（以 `LOOP_DETECTED` 结束的 Run / 全部 Run） | ≤ 5% |

### 2.9 用量统计（不设配额）

- Agent 的任何环节都不设预算或配额，唯一的自动退出机制是死循环检测（见 `10-开发计划/开发计划与里程碑-内部模型版.md` 第 3 节）。
- 统计维度：组织 / 项目 / 用户的 token（使用模型服务返回的真实 usage，含 cached / reasoning token）、模型调用次数、Run 数、耗时。
- 只做统计、展示和异常提醒（例如用量明显高于同类任务的中位数），不拦截新任务，也不暂停或结束运行中的任务。
- 同时运行的 Run 数由 Worker 和沙箱资源决定；资源不足时新任务排队等待，不会被拒绝。

### 2.10 合规

- 数据保留策略按组织配置；支持删除请求（级联删除轨迹和 artifact，只保留审计摘要）。
- 训练数据使用需要项目级授权（`training_authorized`），与 `training/dataset.py:13-14` 的语义一致。
- 模型供应商白名单：组织可以限制代码只发送给已批准的供应商或私有化部署的模型。

### 2.11 部署形态

| 形态 | 方式 | 适用 |
|---|---|---|
| 个人 | `pip install` + `tracefix init`（Windows 可使用 `vendor/` 离线 wheels 和 `start-windows.cmd`） | 单机 |
| 小团队 | `docker compose`：api + worker + postgres + minio | ≤ 20 人 |
| 企业 | Helm Chart：api（多副本）、worker（HPA）、Postgres（托管）、对象存储、OTel Collector | 大规模 |
| 离线 / 内网 | 离线镜像包 + 私有模型网关 | 内网环境 |

### 2.12 用户级可用性清单

| 项 | 标准 |
|---|---|
| 安装 | 一条命令完成安装；`tracefix doctor` 对每项失败都给出可执行的修复建议 |

| 文档 | 本手册 + 快速开始 + 常见问题 |
