# 开发计划与里程碑

> 定位更新：2026-10-07。规划对象为 GUI 检测—修复平台中的 Agent 执行组件。旧独立产品排期、人力合计和企业化阶段已撤出，不作为当前剩余工作量。

## 1. 交付目标

通过接口接收仓库、Profile、规则和任务，执行 Test / Repair，返回 Finding、结构化结果、diff 和证据。上层平台负责用户数据、任务编排、审批、补丁应用与发布；Web / CLI 用于已有能力的调试与兼容。

具体工作包、接口草案与状态以[接口型 Beta 最小补足计划](../00-项目进度/接口型Beta最小补足与开发计划.md)为准。该计划中的拟新增接口不能作为已经可调用的接口引用。

## 2. 里程碑

| 里程碑 | 目标 | 验收条件 |
|---|---|---|
| M0 真实业务闭环基线 | 确认检测、复现、定位、修补与验证主干可信 | 原问题、逆向操作、刷新和正常业务均保持；独立审查接受候选补丁。历史 B01 被拒绝，继续保留为负例 |
| M1 接口型 Alpha | 受控仓库可从程序入口提交 Test / Repair 并取得产物 | 无 TTY / UI 依赖；输入冻结；终态、outcome、验证和补丁语义明确；至少一个真实有效闭环 |
| M2 接口型 Beta | 上层平台可组合检测与指定 Finding 修复 | B0–B5 完成；幂等、按 Run 取消、繁忙 / 重启语义、跨仓库隔离和关键负例通过；唯一最终完整基线与调用说明齐备 |
| M3 Agent 能力增强 | 按实际缺陷扩展代码定位、上下文、记忆、子 Agent 和有界恢复 | 对明确范围提供真实证据与效果对照；不使用 fixture 结果替代真实业务收益 |

M0 的历史“三个有效真实用例”等扩展验收记录仍保留；接口型 Beta 的最小真实闭环门槛以 B5 为准。调整范围不把历史未通过记录改为通过。稳定发布后继续提升支持范围和可靠性，不增加独立平台能力作为成熟度等级。

## 3. 开发顺序

1. B0：统一发布 revision、Run 身份、输入输出契约和恢复接缝。
2. B1：仓库注册、Profile / revision 冻结和仓库 / Run 隔离。
3. B2：只读 GitHub MCP 接入，支持真实授权仓库读取。
4. B3：规则快照 → Finding → Repair 来源链。
5. B4：异步任务 API、幂等提交、状态 / 结果 / 事件 / artifact 查询和指定 Run 取消。
6. B5：真实业务闭环、负例、两仓库隔离、发布说明和最终基线。

B2 / B3 / B4 可以围绕统一契约开发，最终验收依赖 B1 的环境隔离。估算按已交付代码与剩余接缝重新核查，不直接沿用旧人周或日历日期。

## 4. 质量门禁与风险

- 每包完成只执行必要的定向检查；整个开发集成完成后执行一次完整基线，保留准确 revision、环境和原始结果。
- 原问题修复不能通过删除业务能力、放宽断言或修改独立 Oracle 达成。
- 提交成功、任务结束和退出码不能替代 outcome、规则覆盖及当前补丁验证。
- 未知副作用、过期观测、取消与资源不足必须有明确行为，不自动重放或假报成功。
- 凭据、源码 / 产物归属、测试数据重置和模型 / 浏览器环境是接入风险；支持范围先限定在受控 React / TypeScript 项目。

内部模型、可选视觉工具及相关运行保护见[内部模型版](开发计划与里程碑-内部模型版.md)。训练、标注和完整消融作为独立研究专题，不构成接口组件的上线门槛。
