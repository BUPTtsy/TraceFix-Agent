# 开发计划与里程碑（内部模型版）

> 定位更新：2026-10-07。本文只保留 Agent 组件的内部模型接入与运行保护。主开发顺序统一为接口型 Beta 的 B0–B5；旧独立平台工作包、排期与人力合计已撤出。
> 实现与真实验收以[完成度评估](../00-项目进度/完成度评估.md)、[差距清单](../00-项目进度/差距清单.md)的证据为准。历史测试数字保持原口径，本轮 Task 接口与最小测试以本次实际交付记录为准。

## 1. 范围

TraceFix 是单纯 Agent 组件，按仓库管理地址 / 执行凭据、检查规则、Task 定义和 Run 执行记录，提供 GUI 检测、复现、定位、局部修补、验证和证据返回。接口默认创建 Task 后由单独接口启动，首版 Task API 固定 `executionMode=batch`，不创建依赖审批的 interactive Task；`create_and_start=true` 可合并；活动任务编辑返回 409，已停止任务编辑后回到 `created`，每次启动创建新 Run。旧 CLI / 旧 Run interactive、REVIEW 和 continue 兼容保留。保留 PydanticAI、LangGraph、受限工具、上下文 / 记忆、只读调查及可选 GUI Scout 的执行边界。

组件不感知或判断用户身份、角色和权限，也不要求调用平台建设用户管理。调用方传入执行所需的信息，Agent 校验仓库访问凭据、文件 / URL 范围、规则归属、源码版本与工具副作用；结果由调用方消费。Web / CLI 只承担现有调试与兼容用途。

当前 SQLite 保存 Task、Run 索引、规则和知识等部分元数据，后续迁移至 MySQL。仓库注册仍来自 YAML / JSON 与 Profile；PostgreSQL 执行状态、审计和 checkpoint 保留现有职责，不因该迁移计划被描述为 SQLite 或 MySQL 已实现。

本路线使用部署方提供的模型，不开展模型训练。reasoning / usage 是服务实际返回的审计数据，不证明训练样本已经生成；SFT / RL 研究见轨迹专题。

## 3. 运行限制：Run 计量与单次交互保护分层

### 3.1 原则

1. **Run 累计不设预算**：累计模型调用、浏览器动作、token、费用、补丁、子任务等 Usage 用于观测。此原则不取消单次模型请求的尝试上限、工具交互轮次上限或操作超时。
2. **只计量，不拦截**：用量照常记录，在 CLI（`/usage`）和 Web 上展示，用于观测和统计。用量高低都不会暂停或结束 Run。
3. **循环与未知结果分开处理**：重复且无进展可记为 `LOOP_DETECTED`／`ABNORMAL`；`UNKNOWN_OPERATION` 或需核查的 MCP 失败不自动重放，不能被循环检测覆盖。交互模式暂停核查；batch 输出 `FAILED / INFRA_FAILURE`，保留故障和核查标记。
4. **错误处理分模式**：按第 3.4 节分别反馈、有限重试、暂停或收尾。batch 连续三轮诊断/补丁无效后输出 `REPAIR_EXHAUSTED`，重大模型/浏览器故障输出 `INFRA_FAILURE`；这些是错误恢复保护，不以 Run 累计 Usage 作为终止依据。
5. **人工控制**：交互模式保留暂停、取消和审批；batch 的六类验证通过后直接输出报告及 diff，不创建提交。候选补丁的应用与发布由上层平台处理。

### 3.3 死循环检测

现有检测器在安全边界使用运行时的状态、动作、错误与无进展信号（`backend/packages/agent/src/tracefix/runtime/engine.py`），不调用模型；状态指纹已包含复现/验证位置与诊断反馈轮次。下表仍是 Agent 能力扩展 的完整验收目标，补丁重复、按项目配置阈值等尚不能声明全部交付。未知结果先按第 3.2 节暂停或失败收尾，不自动重试，也不改写为循环结论。

| 信号 | 判定方式 | 预警 | 判定为循环 |
|---|---|---|---|
| 状态重复 | 状态指纹 = 阶段 + 页面快照摘要 + 待执行动作 + `patch_hash` + 最近一次失败签名；统计同一指纹在本 Run 中出现的次数 | 第 2 次 | 第 3 次 |
| 动作周期 | 最近的动作序列按周期重复，周期长度 1-4（例如 A→B→A→B） | 重复 2 个周期 | 重复 3 个周期 |
| 补丁重复 | 新补丁与本 Run 中已验证失败的补丁相同（`patch_hash` 一致）；或补丁在同一验证项上以相同的失败签名连续失败 | 首次出现 | 相同补丁第 2 次出现；或相同失败连续 3 次 |
| 错误重复 | 同一错误（类型 + 规范化后的消息）连续出现，期间状态指纹没有变化。包括策略拒绝、输出校验失败、工具报错、可重试的基础设施故障 | 3 次 | 5 次 |
| 无进展 | 连续若干步没有进展事件。进展事件包括：新的页面状态、新证据、新的失败签名、验证推进到下一项、补丁通过的验证项比之前多 | 20 步 | 40 步 |

阈值统计的是**重复次数**，不是用量；进展信号用于避免中断正常推进的任务。当前默认值由 Engine 常量定义，按项目配置和完整长进展零误判验收仍是剩余工作，需用真实基线与评测集校准。

**完整验收目标**（当前已有 `loop.suspected` / `loop.detected` 和循环证据，展示与续跑计数重置仍需逐项验收）

1. **预警**：发出 `loop.suspected` 事件；在下一次模型调用的受保护上下文中注入「检测到重复」提示，列出重复的动作、补丁或错误，要求换一种做法；CLI 和 Web 同时提示用户，用户可以追加提示或暂停。Run 继续运行。
2. **判定**：发出 `loop.detected` 事件，保存循环证据（重复的指纹序列、涉及的步骤范围、相关补丁和错误）；在下一个安全边界进入 FINALIZE，结果为 `LOOP_DETECTED`，状态为 `ABNORMAL`，并释放沙箱。
3. **后续执行**：调用方查看循环证据后可编辑终态 Task 并启动新 Run，按新定义重新开始；若需要保持原工作区、冻结规范和来源，可使用现有 `/api/runs/:id/continue` 或 CLI `/continue RUN_ID 提示` 续跑，循环证据注入上下文并重置检测计数。这两种路径由调用方明确选择，不自动盲重放未知副作用。

### 3.4 错误处理：当前基础与规划

| 错误 | 现状 | 调整 |
|---|---|---|
| 策略拒绝（越权 URL、未授权动作、不允许修改的路径） | 浏览器执行前拒绝返回 `executed=false`；ToolRegistry 全批校验，PermissionError/GuidanceRejected 反馈给模型重新决策，不执行被拒绝动作 | 继续验证不同工具和编辑约束路径，不自动扩大权限 |
| 完整性校验失败（补丁在验证或审批后被改动、作用域发生变化） | 冻结文件、作用域和 patch hash 已有校验；部分错误仍进入通用 PermissionError 反馈路径 | 按错误来源区分策略反馈与不可安全继续的完整性故障；后者需保留核查要求，分别暂停或失败收尾 |
| 模型输出不合格 | 网关在单次总尝试上限内反馈校验错误，已完成工具结果保留；Engine 诊断/补丁阶段补充上下文，batch 三轮仍无有效补丁收尾为 `REPAIR_EXHAUSTED` | 验证反馈、历史工具不重放和候选 diff 标记；不自动切换协议 |
| 重放时元素无法绑定 | 已有 `ReplayUnbound` 返回探索／诊断的处理；frozen press 会绑定当前观测后经 policy/MCP 执行 | 继续验证剩余场景，不能沿用旧「必定 INCONCLUSIVE」预期 |
| 验证门禁拒绝证据 | VERIFY 清空失效验证引用，从第一项重新验证；FINALIZE 再核对当前 diff/hash 与证据，失效时不能输出已验证修复 | 已有实现；补齐故障场景和真实验收，不将有限规范通过等同于产品行为正确 |
| 其他基础设施故障（容器、构建、网络、模型服务限流） | 明确未发送的请求由宿主判断是否安全恢复；Engine 对可继续的错误反馈，batch 对重大异常 `INFRA_FAILURE` 收尾，interactive 对不能安全继续的通用异常 PAUSED | 继续按确定性结果与副作用逐项验收，不把所有网络错误视为可安全重试 |
| 受保护的上下文区块超出模型窗口（例如用户引导过长） | ContextAssembler 先压缩可选区块；保护区块仍超 token 窗口时抛 ContextWindowError，interactive PAUSED、batch 失败收尾 | 核对 manifest、提示和核查信息，补齐真实 tokenizer/窗口场景 |
| 执行循环之外的未捕获异常 | CLI 对 interactive 转 PAUSED 并记录核查要求；batch 尽可能 `finish_error → finalize` 导出报告与 diff | 继续检查 finalize 本身失败与跨进程恢复，不预先承诺任意 checkpoint 均可恢复浏览器状态 |
| 结果未知、网络中断 | interactive 的 `UNKNOWN_OPERATION`/需核查 MCP 失败先 PAUSED；确定 not_sent 才允许历史恢复；batch 失败收尾并保留核查原因 | 不重放未知副作用，不绕过核查要求，不被 student fallback 或循环判断覆盖 |

仅适合继续执行的已知错误参与重试与循环判断；未知结果暂停具有更高优先级，不能因同一错误反复出现而丢失核查要求。

### 3.5 保留的机制（不属于预算）

| 机制 | 作用 | 保留的理由 |
|---|---|---|
| 单次操作超时（浏览器调用 45 秒、Gateway 默认 240 秒，可由 `TRACEFIX_MODEL_TIMEOUT` 配置；clone/沙箱命令另有超时） | 发现卡住的单次操作 | 按结果确定性重试、暂停或失败收尾，不限制 Run 的总时长和总用量 |
| 模型请求尝试与工具交互轮次 | 默认 3 次总尝试、40 轮工具交互，安全恢复时历史轮次继续计数 | 防止一次交互无限重发或执行工具；不限制 Run 累计 Usage |
| 复现判定（3 次重放中至少 2 次一致） | 判断缺陷能否稳定复现 | 这是判定规则；不稳定时以 `INCONCLUSIVE` 结论结束 |
| 上下文窗口分区与内容截断（快照、工具结果、Skill 正文、评论） | 让单次请求放得进模型窗口 | 窗口是模型本身的限制；超出时压缩，不结束 Run |
| 并发与限流（子 Agent 信号量、Worker 数量、客户端限流） | 适配沙箱和模型服务的容量 | 超出时排队，不拒绝，也不结束 Run |
| 补丁范围约束（任务说明书中的最大文件数、行数，以及 L2 约束） | 用户对改动范围的要求 | 超出时补丁被拒绝并反馈给模型，不结束 Run |

### 3.6 当前结果、状态与批处理输出

- **结果**：当前已有 `LOOP_DETECTED` 与 `BUG_CONFIRMED`，继续保留 `REPAIR_EXHAUSTED`、`POLICY_BLOCKED`、`INFRA_FAILURE`；旧的「删除三种结果」规划已不符合实现。test 模式稳定复现输出 `BUG_CONFIRMED`；`INCONCLUSIVE` 也用于证据不足等情况，不能限定为复现不稳定。
- **状态**：保留 `FAILED`，循环使用 `ABNORMAL`，确认改目标后父 Run 使用 `SUPERSEDED`。batch 无效诊断耗尽及重大故障输出 `FAILED`，人工取消仍为 `CANCELLED`；成功结论为 `COMPLETED`。
- **转移**：`ReplayUnbound` 会回探索/诊断重新录制；batch 六类验证通过后从 VERIFY 直接 FINALIZE，不等待本地提交审批。interactive 仍进入 REVIEW，只有绑定的人工审批才可创建本地候选提交；没有远端发布。
- **续执行**：`can_continue` 支持 `ABNORMAL`、`FAILED`、`CANCELLED` 及非成功结论的 `COMPLETED`，拒绝普通续跑 `FIX_VERIFIED`/`NO_BUG_FOUND`。续执行按本次 CLI 策略执行，不被历史 interactive 配置覆盖；外部评审反馈通过新的任务或受限引导输入。
- **输出**：batch 始终尽可能导出最终报告、候选 diff 与 `BATCH_RESULT` JSON。空 diff 为 `patch_available=false / patch_verification=none`，非空但未全验证为 `unverified`，只有当前 hash 和六类证据有效才为 `verified`；`--run` 对 `COMPLETED` 返回 0、其他终态返回 1，启动失败返回 2。稳定任务型 API 结果契约仍需 B4 验收，完整 CLI NDJSON 不是发布门槛。
- **验收边界**：冻结 TestSpec/复现计划的自动通过只证明规范覆盖的条件。B01 已显示逆向行为遗漏会产生无效修复，必须另有独立业务回归与产品审查，才可计入业务成功指标。

## 4. 双模型架构：感知与决策分离（方案 B）

本节是待实现的目标架构。现有配置支持文本/视觉模型名和直接带图请求，尚无 `vision_request`、`VisionReport`、`vision.inspect` 或自动 A/B 路由；已有通用工具框架可作为后续接入基础。

```text
              ┌──────────── 编码模型（无图；支持 tools / json_schema）────────────┐
观测 ────────▶│ 输入：压缩后的 a11y 快照 + console / network + 视觉结论（文本）      │──▶ 动作 / 补丁 / 计划
（文本部分）   └───────────────────────────────────▲─────────────────────────────┘
                                                  │ VisionReport（JSON 或降级文本）
截图 ──▶ 多模态模型（看图工具，按需调用）─────────────┘
```

**分两步落地**

| 版本 | 时间 | 内容 |
|---|---|---|
| v1 | 可选 v1 | `Decision` 契约新增可选字段 `vision_request {question, region?}`；运行时调用多模态模型，把 VisionReport 放进上下文后重新决策。快照信息不足时自动触发（可交互元素过少，或存在大面积没有可访问名称的 canvas / img） |
| v2 | 可选 v2，依赖工具框架 | 迁移为 `vision.inspect(question, screenshot_ref, region?)` 工具；接入 `visual` 类检测规则；VERIFY 阶段对视觉类 Finding 做修复前后截图对比 |

- **调用控制**：不设次数上限，按需触发；同一截图、同一问题的结果缓存复用；截图先缩放和裁剪再发送。反复对同一画面提同一个问题属于重复动作，由死循环检测处理（第 3 节）。
- **输出契约**：`VisionReport {answer, findings[{description, bbox?, confidence}], raw_text, structured}`。多模态模型支持结构化输出时直接使用；否则在提示词中要求 JSON 并宽松解析，失败重试 1 次；仍失败时把原文放进 `raw_text`，并标记 `structured=false`。
- **可信边界**：视觉结论只作辅助证据，可以生成 `suspected` 状态的 Finding、引导探索方向，但不能单独判定 VERIFY 通过或失败。视觉类修复进入审批时，展示修复前后截图和视觉结论，由人工确认。
- **对照与回退**：方案 A 可复用显式视觉模型带图路径，但仍需验证服务兼容性。接入该扩展时在同一评测集上取得 A/B 对照；`decision_model` 切换开关仍需实现，不能凭现有模型名配置认为已具备自动回退。

## 5. GitHub 与仓库接入边界

仓库来源限制、只读 GitHub MCP、Profile / revision 冻结与来源校验按 B1 / B2 开发。仓库配置管理地址、访问凭据引用及执行范围；调用方可预置普通 checkout，秘密由部署方解析，不进入目标、提示词或模型上下文。

Agent 返回 diff 与验证证据。自动 PR、评审轮询和评论回复不属于组件交付范围；外部评审意见转为新 Task 或现有 Guidance 时，必须重新绑定来源、范围与验收规范。仓库访问失败按凭据 / 资源错误报告，不映射为用户角色权限。

## 6. 工作包与里程碑

唯一主计划为 B0 基线 / 契约 → B1 注册 / 冻结 / 隔离 → B2 只读 GitHub MCP、B3 规则 / Finding 来源、B4 任务 API → B5 真实验收。详细输入输出、接口与估算见[接口型 Beta 计划](../00-项目进度/接口型Beta最小补足与开发计划.md)。

内部双模型、完整多语言代码情报、长期记忆收益和多 Agent 效果按实际业务需要追加；不得因其尚未完成把平台管理能力重新加入发布门槛。

## 7. 组件指标与验证

记录检测覆盖、复现率、独立审查接受的真实修复率、业务回归、阶段耗时、请求 / 工具错误、token 用量和人工核查次数。分母、源码 revision、Profile、模型服务及证据范围必须明确；历史 fixture、定向测试和自动报告不代替产品行为正确性。

接口上线最小门槛为 B5 的一个真实有效闭环、关键负例和两仓库隔离。held-out / 四格、恢复率与长期记忆实验单独保留待验收状态，不据文档收敛提前关闭。

## 8. 开发与交接纪律

每部分只跑必要的定向检查；完成最终集成后只跑一次完整基线。交付说明明确已有接口和拟新增契约、支持范围、准确 revision、环境条件、真实证据与限制。文档变更由用户手动提交，不自动 commit 或 push。
