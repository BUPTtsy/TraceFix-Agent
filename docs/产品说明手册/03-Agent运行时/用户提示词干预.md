# 用户提示词干预

包含两部分：**任务开始时**用提示词细粒度地派发任务，以及**运行过程中**用提示词调整 Agent 行为。

## 1. 现状

### 1.1 初始派发

| 入口 | 形式 | 证据 |
|---|---|---|
| CLI 一次性执行 | `--run --goal "<一句话目标>"` | `cli/main.py:599-673` |
| CLI REPL | 输入纯文本作为目标，再执行 `/run` | `cli/main.py:432-434` |
| Web | AgentDock 表单：goal + mode（test/repair）+ projectId | `backend/apps/console-api/server/index.mjs:186-192` |
| 手写 TestSpec | `--spec file.json` | `profiles/persistence.spec.json` |

`goal` 属于不可变字段（`contracts.py:252`），PREPARE 阶段由模型把它编译为 TestSpec 并冻结（`contracts.py:262-264`）。目前**没有结构化的任务说明书**：无法一次派发多个场景、限定页面/文件范围、指定规则集或交付要求。

### 1.2 运行中干预

| 操作 | 实现 | 实际效果 | 证据 |
|---|---|---|---|
| `/pause`、`/cancel`、`/interrupt` | 设置 `engine.control` | ✅ 在下一个安全边界生效 | `cli/main.py:467-471,537-546`、`engine.py:326-333` |
| `/approve`、`/reject` | 恢复 REVIEW 节点的 `interrupt()` | ✅ | `cli/main.py:551-558` |
| `/resume RUN_ID` | 从 PAUSED / WAITING_APPROVAL 恢复 | ✅ | `cli/main.py:371-397` |
| Run 运行中输入文本 | 追加到 `engine.notes` | 🔴 **只记录为事件，不进入模型上下文** | `cli/main.py:421-425`、`engine.py:335-338` |
| PAUSED 时输入「纠正提示」 | 追加 notes 并自动恢复 | 🔴 同上，只触发恢复，内容不生效 | `cli/main.py:426-431` |
| `/continue RUN_ID 指令` | 对非成功结束的 Run 续跑：沿用同一个 `run_id` 和工作区，`revision`、`continuation_count` 加一 | ✅ 指令作为 `user_continuation` 注入上下文；`FIX_VERIFIED`、`NO_BUG_FOUND` 的 Run 不能续跑 | `engine.py:139-140`、`runtime/continuation.py:6-32`、`cli/main.py:263-265` |

结论：在运行中调整 Agent 行为，目前唯一有效的方式是「结束当前 Run，再用 `/continue` 续跑」。`build_context` 里没有承载用户引导的字段（`knowledge/context.py:15-36`）。Web 端完全没有运行中干预入口。

## 2. 目标设计 📐

### 2.1 任务说明书（Task Brief）

用于初始的细粒度派发，支持 Markdown frontmatter 和 YAML 两种写法。CLI 通过 `--brief` 传入；Web 通过「新建任务向导」生成同样的结构。

```yaml
---
repo: acme/shop-web
base: main
mode: repair                      # test | repair
rule_sets: [checkout-baseline, a11y-basic]
scope:
  urls: ["/cart", "/checkout/*"]
  include_paths: ["src/features/checkout/**", "src/components/form/**"]
  exclude_paths: ["src/legacy/**"]
constraints:
  max_files_changed: 5
  max_lines_changed: 120
  forbid: ["修改 API 契约", "新增依赖"]
scenarios:                         # 可选；不写时由 PLAN 阶段根据正文和规则自动拆解
  - id: s1
    goal: 购物车数量改为 0 后应移除该商品，刷新后依然不在
    priority: high
  - id: s2
    goal: 结账表单缺少必填项时，提交按钮旁应出现错误提示
    priority: medium
acceptance:
  require: [unit, build, original, regression, rules]
delivery:
  publish: auto-draft              # manual | auto-draft
  branch_prefix: tracefix/
  pr_labels: [bot, needs-review]
  reviewers: ["@frontend-lead"]
---
补充说明（自由文本）：最近重构了表单组件，重点关注 FormField 的受控/非受控切换。
```

处理流程：

1. **解析与校验**：pydantic `TaskBrief` 契约。`scope` / `constraints` 只能在 Profile 权限范围内**收窄**，不能扩大。`constraints` 中的文件数、行数是对补丁范围的约束，不是预算：补丁超出时被拒绝并反馈给模型，不会结束 Run。任务说明书中没有预算字段（不设预算，见 `10-开发计划/开发计划与里程碑-内部模型版.md` 第 3 节）。
2. **PLAN 阶段**：模型把正文和 `scenarios` 整理成执行计划（场景列表、依赖顺序、预计用量）。预计用量只供参考，不作为上限。
3. **计划确认点**：CLI 展示计划后提示 `确认执行? [Y/n/e编辑]`，Web 显示计划卡片，每个场景可以单独勾选或编辑。
4. 确认后，每个场景生成一个 Run，场景 goal 仍在该 Run 内冻结，保持现有不可变语义。

### 2.2 运行中干预分级

| 级别 | 类型 | 示例 | 处理 | 生效时机 |
|---|---|---|---|---|
| L0 | 控制 | 暂停 / 继续 / 取消 | 沿用现有 `engine.control` | 下一个安全边界 |
| L1 | 提示（hint） | 「先看 FormField 组件」「注意是刷新后才出现」 | 注入受保护上下文区块 `user_guidance` | 下一次模型调用 |
| L2 | 约束（constraint） | 「不要改 src/legacy」「补丁不超过 50 行」 | 转成策略收窄规则，由 `Workspace` / `Policy` 强制执行；只能收窄 | 立即（写入 RunState） |
| L3 | 改目标（retarget） | 「其实问题在结算页，不是购物车」 | 需要重新冻结 TestSpec：当前 Run 以 `SUPERSEDED` 结束，派生子 Run 继承证据 | 用户二次确认后 |

分类方式：

- 显式命令：`/hint`、`/constrain`、`/retarget` 直接指定级别。
- 自由文本：由轻量模型分类，并把分类结果回显给用户（如「识别为：提示 L1，将在下一步生效」）。L3 必须经用户确认，分类置信度低时默认按 L1 处理。
- PR 评审意见：PR 创建后，评审人的意见是另一类提示词来源。先由文本模型用单独的 system prompt 整理成提示词，并按同样的 L1 / L2 / L3 分级；人工确认后启动修订 Run。详见 `PR评审意见驱动修复.md`。

### 2.3 Guidance 数据结构与注入

```python
class Guidance(Contract):
    id: str
    run_id: str
    author: str                 # 用户 id（企业模式来自登录身份）
    level: Literal["hint", "constraint", "retarget"]
    text: str = Field(max_length=2000)
    created_at: float
    applied_step: int | None    # 首次注入的 step
    expires: Literal["run", "phase", "once"] = "run"
    status: Literal["queued", "applied", "acknowledged", "rejected", "superseded"]
```

- `build_context` 新增 `user_guidance` 字段。它和 `goal`、`test_spec` 一样属于受保护区块，不会被压缩裁剪，只保留未过期的条目。
- 模型输出契约（`Decision`、`PatchProposal` 等）新增可选字段 `guidance_ack: list[{id, how_applied}]`，模型需要说明如何采纳每条引导。
- 事件：`guidance.queued` → `guidance.applied` → `guidance.acknowledged`。这些事件进入轨迹，是训练「可引导性」的高价值数据。
- 安全边界：用户引导属于可信指令，优先级高于知识文档和网页内容，但低于系统策略和冻结的 TestSpec。引导**不能**扩大权限，也不能跳过验证门禁；遇到这类请求时，状态标为 `rejected` 并告知用户原因。

### 2.4 交互入口

| 入口 | 操作 |
|---|---|
| CLI REPL | 运行中直接输入文本（自动分类）；`/hint 文本`、`/constrain 文本`、`/retarget 文本`；`/guidance` 查看各条引导的状态 |
| Web 运行详情页 | 右侧「对话与干预」面板：输入框 + 级别选择（提示 / 约束 / 改目标），每条消息显示状态标签（排队 / 已注入 / 已采纳 / 被拒绝） |
| API | `POST /api/v1/runs/{id}/guidance`、`GET /api/v1/runs/{id}/guidance` |

### 2.5 验收标准

1. 运行中发送 L1 提示后，下一次模型请求的 artifact 中能看到该条 `user_guidance`，模型响应里有对应的 `guidance_ack`。
2. L2 约束生效后，违反约束的补丁会被 `Workspace.apply` 拒绝，并返回结构化错误。
3. L3 确认后，父 Run 标记为 `SUPERSEDED`，子 Run 的 `parent_run_id` 正确，并复用已验证的证据。
4. 所有引导都能在轨迹导出中还原：注入位置、模型如何响应、最终效果。
