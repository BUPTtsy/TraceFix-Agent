# Skill 加载与推理成本

本说明针对当前 TraceFix 单目录 Skill 机制。模型实际行为取决于所选服务；公共前缀相同只代表具备复用条件，不等于服务已经命中缓存。

## 加载过程

1. 从配置根目录的 `*/SKILL.md` 建索引，默认目录为 `backend/skills`。
2. 按模型调用的当前阶段过滤，再按框架、规则类别和文件路径匹配。不同触发维度取交集，同一维度内取并集；空触发器在允许阶段直接匹配。
3. 规则摘要携带类别；已有源码卡片用于定位相关文件，缺少卡片与显式文件列表时用授权工作区文件集合进行内部匹配。
4. 将本阶段的名称与描述放入 system 索引，将选中的完整正文放入 user context。受信调用方仍可通过 `load_skills` 显式选择阶段允许的 Skill；模型尚无独立读取 Skill 的工具。
5. 原生浏览器工具返回新观测后重新计算适用规则和 Skill，移除已经不匹配的正文。

`phases` 说明模型什么时候需要这份指导。运行时在 `DIAGNOSE` 生成 `PatchProposal`，所以最小补丁指导必须能在该阶段加载。验证和报告指导用于前期计划、诊断及证据摘要；实际补丁应用、验证门、人工作业决定和最终报告生成仍由确定性代码执行，不增加额外模型调用。

## 两种缓存

| 缓存 | 缓存内容 | 失效原因 | 直接收益 |
|---|---|---|---|
| 本地 Skill 文件缓存 | 解析后的元数据、完整正文和内容哈希 | 文件新增、修改、删除或替换 | 减少磁盘读取、YAML 解析和重复哈希计算 |
| 供应商 prompt 前缀缓存 | 相同输入前缀的模型计算状态 | 前缀内容或结构变化、缓存过期、路由等服务因素 | 可能降低命中输入的费用和首 token 延迟 |

本地缓存不会减少模型实际收到的 token；缓存的正文仍随请求发送。目录仍执行文件枚举及状态检查，不是零 I/O。缓存使用文件状态识别变化；外部工具若刻意保留所有用于比较的文件状态，不能把该缓存当作内容完整性监控。

请求布局按以下顺序组织：

```text
system：共同策略 → 输出契约 → 项目 AGENTS 指令 → 本阶段 Skill 名称/描述
user：输出 JSON schema → context.skills 全文 → 其余动态 context
后续：assistant / tool 历史
```

确定性序列化避免仅因字典插入顺序不同而改变请求。正文保留在 user context，不提升为 system 权限；数组顺序可能表达业务含义，不能为了缓存任意重排工具历史、步骤或证据。

同模型、相同输出契约、相同项目指令、相同 Skill 集合与版本的请求，即使观测发生变化，也有机会复用一直到 Skill 正文结束的公共前缀。阶段切换、输出契约切换或 Skill 内容变化时，第一次差异之后的内容无法继续作为同一个连续前缀复用；差异之前的公共部分仍可能复用。即使后文出现完全相同的正文，也不能假设服务会把它作为独立文本块命中。

当前索引仍按阶段变化，动态观测仍会刷新原始 user context。该布局没有保证跨阶段整段命中，也没有实现所有工具轮次只追加消息。最低缓存长度、缓存粒度、生命周期、路由和工具定义如何参与前缀匹配都由实际服务决定；需要查看真实 usage。

请求尚未发送而暂停时，恢复使用最后一次已持久化请求的上下文，保留对应 Skill 正文和版本；恢复后执行了新的浏览器工具，才继续按新观测重新选择。这样不会在重试时用重新组装的上下文覆盖已有工具历史的输入依据。

## 离线检查结果

在 2026-09-28 工作区的 13 份内置 Skill 上，完整文件共 9,049 个字符。人为提供 React 文件和 `functional`、`a11y`、`visual` 三类规则时，选择结果如下；该输入用于比较机制，不代表每个实际 Run 都具备这些类别。

| 模型消费阶段 | 选中份数 | 正文字符数（含 frontmatter） |
|---|---:|---:|
| PREPARE | 3 | 2,265 |
| EXPLORE | 3 | 1,885 |
| REPRODUCE | 2 | 1,059 |
| DIAGNOSE | 8 | 6,095 |

13 份目录、一次选择 4 份的文件读取检查中，旧实现每次注入读取正文 134 次；缓存后首次 13 次，目录内容未变时下一次为 0 次。这里统计正文读取，不包括目录枚举和文件状态检查。

请求布局测试只改变 observation，Skill 正文为 1,527 个字符：旧布局的 user 消息公共前缀为 42 个字符，新布局为 2,593 个字符，新 user 消息全长 2,775 个字符。两次 system 消息保持相同。字符数不是 token 数，也不是供应商实际命中量；这些检查不能推导节省费用的百分比。

## 收益与代价

| 方面 | 收益 | 代价或限制 |
|---|---|---|
| 上下文相关性 | 阶段和触发器减少不相关指导，保留完整操作步骤 | 触发过宽会引入噪声，过窄会漏选；框架探测含文本启发式 |
| 输入规模 | 不必每次发送全部 Skill 正文 | 修复漏加载后，实际输入通常比原先失效的实现更多 |
| 缓存 | 相同集合的正文放在动态数据之前，增加可复用前缀 | 集合变化仍打断前缀；更高命中率不必然意味着更低总费用 |
| 推理效果 | 明确证据要求和操作流程，可能减少无效动作、返工和重试 | 多份相似指导可能互相干扰；加载器正确不等于模型一定遵循 |
| 可复现性 | 记录每个请求所用 Skill 的版本与哈希 | 文件可热更新，尚未冻结整个 Run 的 Skill 版本集合 |
| 权限与执行 | Skill 只提供指导，执行受既有 policy 和确定性门禁约束 | `tools_hint` 不会注册工具，也不会启动外部子 Agent |

当前没有 Skill 总输入 token 预算、优先级裁剪或全文截断。随着数量增加，需要先测量相关性和完整任务成本，再决定是否引入更细的选择机制。缓存内容仍占用上下文窗口，长上下文仍可能影响注意力计算与生成延迟。

## 成本如何比较

以实际服务计费为准，一个任务的主要成本可写成：

```text
任务成本 = 所有请求之和(
    未命中输入 token × 未命中输入单价
  + 命中输入 token × 命中输入单价
  + 输出/计费推理 token 对应费用
) + 工具与运行环境成本
```

推理 token 是否包含于输出 token、是否单独报告或计费，取决于模型和服务，不能重复计算。前缀缓存主要影响重复输入的处理，不会自动减少模型生成的推理或输出 token。当前默认 DeepSeek 请求显式关闭 thinking；Skill 依然可能通过改变决策和调用次数影响整个任务成本。

阶段选择与全量常驻没有固定的费用优劣。例如只考虑 Skill 部分，若选中 2,000 token 全部未命中，全量 8,000 token 已经全部命中，且命中单价恰为普通单价的 10%，后者本次输入费相当于 800 个普通输入 token，反而更低。这只是算例：它忽略冷启动、其它上下文、缓存期限以及额外正文对任务质量的影响，不能当作当前供应商报价或本项目实测。

建议比较同一任务集、相同模型与参数下的阶段选择和全量常驻，分别观察冷缓存与热缓存。至少记录：

- 每个完成任务的总请求数、工具轮次、重试数和成功率。
- `prompt_tokens`、命中/未命中输入、输出 token，以及供应商实际返回的推理 token。
- 首 token 延迟、完整任务延迟和每个成功任务的费用。
- Skill 清单、版本哈希、阶段、输出契约与对应请求，解释缓存变化来源。

网关原样保存供应商 usage；DeepSeek 的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`、OpenAI 兼容服务的 `prompt_tokens_details.cached_tokens` 可在服务实际返回时用于分析。没有这些字段时应标记为未知，不能把未报告视为命中数为零。离线公共前缀测试验证布局，不测量真实供应商命中率、费用或修复成功率。

## 审计口径与边界

- `skill.loaded`：Run 内首次成功取得某个 `name@version#content_hash`。
- `RunState.skills_loaded`：Run 内曾加载版本的去重清单，不表示当前请求清单。
- `skills.injected`：每次请求尝试实际载荷中的 Skill 清单，关联请求记录、逻辑调用、重试与工具轮次；空清单也有意义。
- 模型请求 Artifact：核对实际序列化正文与上下文的依据。尝试事件产生于发送前，不证明请求被供应商接收或成功完成。

来源仍为单目录；组织、项目、内置资源的同名覆盖尚未实现。缺失目录仍返回空索引，单个非法 Skill 仍会使目录解析失败；frontmatter 解析器对字符串中 `---` 的处理仍有限制。这些边界与本次五项加载链路修复分开追踪。
