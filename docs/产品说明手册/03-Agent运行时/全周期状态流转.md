# Agent 任务与执行状态

> 定位更新：2026-10-07。本文描述 TraceFix 组件内的 Task / Run 流程与调用方交接边界。TraceFix 不管理用户、组织或租户，不读取或判断调用方用户权限；调用方的 PR、评审、审批与发布状态不加入 Agent 主状态机。规则、Task / Run 索引和文档当前使用 SQLite，仓库配置仍包含 YAML / JSON 注册表；SQLite 后续迁移 MySQL。

## 1. Task / Run 的状态维度

Task 表示调用方提交的执行定义，Run 表示一次实际执行。阶段表示 Run 当前执行步骤；运行状态表示活动、暂停或终态；outcome 表示业务结论。调用方消费结果时同时查看三者及验证 / 证据，不以任务结束判断修复成功。

Task 接口生命周期：

| Task 状态 | 可用操作 | 结果 |
|---|---|---|
| `CREATED` | `start`、`PUT` 编辑、`stop`（无活动 Run 时幂等） | `start` 创建新的 Run |
| `RUNNING` / `PAUSED` / `FINALIZING` | `stop`；`PUT` 编辑返回 `409 TASK_NOT_EDITABLE` | 当前 Run 继续使用原冻结快照，除非被停止 |
| `STOPPED` / `COMPLETED` / `FAILED` | `start`、`PUT` 编辑 | 编辑后回到 `CREATED`；再次 `start` 沿用 Task ID 并创建新 Run ID，旧 Run 完整保留 |

`/api/v1/tasks` 已增加基础生命周期接口：`POST /api/v1/tasks` 只创建定义；`POST /api/v1/tasks/{id}/start` 单独启动并新建独立 Run；`create_and_start` 是两步合并的便捷动作。`stop` 针对指定 Task 的当前 Run，重复调用幂等且不能影响其他 Task。稳定 result、持久化幂等和仓库注册仍待补齐。

详细类型与转移以 `runtime/contracts.py`、`runtime/engine.py` 和[主循环与状态机](主循环与状态机.md)为准；稳定接口序列化契约仍按 B4 补齐。

## 2. Test 与 Repair 主干

```text
调用方创建并启动 Test Task
  PREPARE：冻结源码、Profile、规则和 TestSpec，部署测试环境
  EXPLORE：受限浏览器探索、规则检查、记录观测与动作
  REPRODUCE：选择并冻结复现计划，独立重放确认
  FINALIZE：返回 Finding、覆盖、outcome 与证据

调用方选择来源 Finding，创建并启动 Repair Task
  PREPARE / REPRODUCE：校验来源与当前源码，重新复现
  DIAGNOSE：基于症状、源码与证据定位
  PATCH：生成并应用受控候选修改，检查 before_hash / 路径
  VERIFY：验证原问题、业务回归与工程检查
  FINALIZE：返回候选 diff、验证状态、outcome 与证据
  调用方：消费结果 → 自行审阅 / 应用补丁 / 提交 / PR / 发布
```

首版 Task API 仅接受 `executionMode=batch`；`interactive` 返回 HTTP 400，暂无审批端点。Task 的 Repair 验证后直接进入 FINALIZE，返回报告和 diff，不创建提交。原 CLI / Run interactive 模式在 VERIFY 后进入 REVIEW，本地提交须显式审批；该交互分支不适用于 Task API。

## 3. 业务结论与产物

| outcome / 标记 | 调用方应理解为 |
|---|---|
| `BUG_CONFIRMED` | Test 在冻结范围中确认可复现缺陷，尚未修复 |
| `NO_BUG_FOUND` | 充分覆盖的检查未发现问题，不能代表未检查范围 |
| `FIX_VERIFIED` | 当前候选补丁绑定有效验证；由调用方审阅并自行决定应用 |
| `INCONCLUSIVE` | 复现、覆盖或证据不足，不能推断通过 |
| `POLICY_BLOCKED` | 授权或执行策略阻止继续 |
| `REPAIR_EXHAUSTED` / `LOOP_DETECTED` | 无效修补或无进展已收敛，保留失败证据 |
| `INFRA_FAILURE` / 核查标记 | 基础设施失败或结果未知，按实际 error 处理 |
| `CANCELLED` | 任务被取消，已形成产物不自动作废或提升为成功 |

diff 为 `none`、`unverified` 或 `verified` 时必须与当前源码 / patch hash、验证 refs 一致。空 diff、旧验证和模型自报不能成为成功证据。HTTP 2xx 和 `COMPLETED` 不能独立代替 outcome。

## 4. 恢复与再次调用

- 已完成工具结果按 receipt 复用，UNKNOWN 副作用不盲重放；过期观测需要重新观察和绑定。
- 单次请求与工具交互保护、无进展恢复及取消传播独立于 Run 累计用量。
- 现有继续接口只允许支持的非成功状态；成功 Run 的新修复或新目标使用新建 / 派生任务，保留历史来源。
- L3 Guidance 确认后派生 Run，重新冻结目标与验收；继承证据只作输入，不能直接继承成功结论。
- 意外崩溃后的任意浏览器状态不承诺透明恢复；重启后的状态查询、繁忙与按 Run 取消按 B4 验收。

调用方负责把后续评审转换为新的 Task，不要求 Agent 维护 PR 跟踪器、评论通知、用户账户或全局审批中心。TraceFix 只校验仓库 / Run 绑定、执行策略和证据来源，不判断发起请求的用户权限。

## 5. 验收边界

接口型 Beta 至少完成一个真实检测 → Finding → Repair → 验证 → 结果闭环，保持原问题、逆向、刷新和正常业务。历史 B01 被拒绝的自动 `FIX_VERIFIED` 仍为负例。

真实恢复 / 长期效果和 held-out / 四格保留各自待验收状态；定向测试、公开 fixture 与产物数量不能代替这些结果。详细工作包与接口草案见[接口型 Beta 计划](../00-项目进度/接口型Beta最小补足与开发计划.md)。
