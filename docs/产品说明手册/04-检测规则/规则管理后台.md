# 检测规则接口与版本快照

> 定位更新：2026-10-07。沿用原文件名以保持引用。规则由上层平台配置；TraceFix 负责输入校验、版本冻结、适用性筛选、上下文注入与 Finding 来源。

## 1. 组件职责

| 平台提供 | TraceFix 处理 |
|---|---|
| 规则正文、类型、严重级别、适用范围和修复指引 | 按共享 Rule 契约校验，拒绝非法内容与越权范围 |
| 选择规则 ID / 版本或传入任务规则 | 冻结版本与 hash，记录 Run 实际使用快照 |
| 选择检测结果发起修复 | 绑定 Finding、来源 Run、规则快照、仓库及证据 |
| 规则编辑界面、发布权限和审阅流程 | 现有版本 / 状态接口供适配，不建设组织成员或规则管理后台 |

规则不能扩大 `authorized_actions`、`allowed_files` 或网络白名单；模型不能自行忽略必检规则或把未检查视为通过。适用性由运行时按阶段、URL 与文件范围确定。

## 2. 已有接口与存储

当前 Node 服务使用 `/api` 前缀，调用 `backend/packages/console-service` 的规则服务，Python Agent 从同一 SQLite 文件读取快照。

| 方法与路径 | 已有用途 |
|---|---|
| GET / POST `/api/rules` | 按项目、状态、关键字列举；创建草稿 |
| GET / PUT / DELETE `/api/rules/{id}` | 查看、保存新版本、删除未引用规则 |
| POST `/api/rules/{id}:publish` / `:disable` / `:archive` | 带版本检查的状态变更 |
| GET `/api/rules/{id}/versions` | 查看版本历史 |
| POST `/api/rules/{id}:rollback` | 用历史内容创建新版本，不覆盖历史 |
| GET `/api/rules/{id}/findings`、`/api/rules/insights` | 查询命中与质量数据 |
| GET / POST `/api/rule-sets` | 规则集基础记录 |
| POST `/api/runs/{id}/derive` | 继承父规则快照，可通过 `additionalRuleIds` 追加规则 |

规则、版本、Finding 与知识文档使用独立记录；规则不经过知识库的模型选择。控制台与 Agent 必须使用同一 SQLite 路径。来源字段与校验依据见 `backend/packages/console-service/src/rules.ts`、Python `rules/`。

拟统一的 `/api/v1/rules` 和指定 Finding Repair 接口属于 B3 / B4 开发计划，不能把现有 CRUD 等同于稳定外部闭环已完成。契约见[接口型 Beta 计划](../00-项目进度/接口型Beta最小补足与开发计划.md)。

## 3. 规则到 Finding 与 Repair

1. 在 Run 创建时冻结规则 ID、版本、内容 hash 和适用范围。
2. 每次模型请求前更新受保护的 `detection_rules`，记录 `rules.injected` 和实际上下文来源。
3. oracle / static / guided 规则按各自执行方式形成覆盖记录、疑似结果或 Finding；疑似命中不能等同于可修复缺陷。
4. 平台选择 Finding 后，Repair 校验来源仓库 / Run 与规则快照，重新复现并保留来源链。
5. PATCH 仍使用相关规则和 fix_guidance；VERIFY 同时检查原问题、规则覆盖和业务回归。

尚需按 B3 验收真实规则闭环、错来源 Run 拒绝、PATCH 上下文保持和跨仓库隔离；不以规则页面存在代替这些验收。

## 4. 现有调试页面

`frontend/packages/rules/src/RulesPage.tsx` 提供列表、JSON 配置编辑、版本、启停 / 归档、质量统计及单规则注入预览。首次初始化有 5 条内置演示规则。页面用于本地查看和验证接口，不承担平台规则权限或后台数据管理。

已被 Run / Finding 引用的规则不能物理删除；旧快照不被后续版本覆盖。追加规则创建派生 Run，不修改父快照；父 Run 缺快照时拒绝派生。前台细节见[规则中心调试页面](规则中心前台需求.md)。

YAML 编辑器、locator 点选、规则试运行 UI、标注看板和组织级规则继承不列为组件发布缺口。
