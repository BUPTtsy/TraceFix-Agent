# 规则管理后台

## 1. 现状

历史版本没有独立的规则管理后台，知识文档的管理入口分散在两处：

| 能力 | Web（KnowledgePage） | CLI（`/knowledge`） | 证据 |
|---|---|---|---|
| 列表 / 查看 | ✅ | ✅ `list` / `show` | `demo/bugboard/src/components/KnowledgePage.tsx`、`cli/workspace.py:220-317` |
| 新建 / 编辑 | ✅ 编辑器 | ✅ `new` / `edit` | 同上 |
| 上传导入 | ✅ .md / .markdown / .txt | ✅ `import` | 同上 |
| 启用 / 停用 | ✅ 复选框 | ✅ `enable` / `disable` | `cli/workspace.py:266-276` |
| 检索预览 | ✅ | ✅ `search` | `POST /api/knowledge/search` |
| 导出 | 🔴 | ✅ `export` | `cli/workspace.py:271-273` |
| 删除 | 🔴 | 🔴 | `console.py` 的 dispatch 中没有 delete |
| 版本历史 / 回滚 | 🔴（只有当前版本号） | 🔴 | `documents.py:92` |
| 优先级 / 严重级别 / 适用范围 | 🔴 | 🔴 | — |
| 命中统计 | 🔴 | 🔴 | — |
| 权限 | 单 token 或 loopback，无角色 | 本机用户 | `demo/bugboard/server/index.mjs:52-74` |

当前版本已经在 BugBoard 中提供规则中心（`#rules`），后端接口由 Node 控制面直接调用 `console-ts` 的规则数据服务。规则中心与知识库共用本地 SQLite 文件，但规则记录、版本和 Finding 使用独立表，不会混入知识文档检索。Python Agent 继续从同一文件读取规则快照。

## 2. 目标设计 📐

### 2.1 页面结构

```text
规则中心
├── 规则列表          /rules
├── 规则详情/编辑      /rules/:id
├── 规则试运行        /rules/:id/test
├── 规则集            /rule-sets, /rule-sets/:id
├── 命中与质量        /rules/insights
├── Skill 管理        /skills              （与规则共用发布流程）
└── 审计日志          /rules/audit
```

### 2.2 规则列表页

| 区域 | 内容 |
|---|---|
| 筛选栏 | 作用域（组织 / 项目 / 任务）、类别、严重级别、类型（oracle / static / guided）、状态、标签、负责人、关键字 |
| 表格列 | 名称、类型、类别、严重级别、优先级、作用域、版本、状态、近 30 天命中数、误报率、最后命中时间、负责人 |
| 行内操作 | 编辑、复制、试运行、启用/停用开关、查看历史 |
| 批量操作 | 启用、停用、加入规则集、导出、归档、删除（需二次确认；已被历史 Run 引用的规则只能归档，不能物理删除） |
| 顶部按钮 | 「新建规则」、「从模板创建」、「导入（YAML/JSON）」、「导出全部」 |

### 2.3 规则编辑器

- **双模式**：表单模式（面向普通用户）和 YAML 模式（面向高级用户），两者实时同步，并用 JSON Schema 校验。
- **类型专用编辑区**：
  - oracle：可视化条件构建器（触发动作 → 期望元素 / console / network 条件），带 locator 选择器，可以从历史 Run 的快照里点选元素。
  - static：查询编辑器（tree-sitter query 或 Semgrep pattern），右侧实时显示在所选项目上的匹配结果。
  - guided：正文编辑器 + token 计数 + 「违反示例 / 合规示例」输入框。
- **作用域选择器**：项目多选、URL 模式、路径 glob（带实时匹配预览：「当前匹配 23 个文件、4 个路由」）。
- **保存**：生成新版本，必须填写变更说明；`draft` 状态的规则不会进入任何 Run。
- **敏感信息扫描**：保存前检测密钥、token、内网地址，命中时阻止保存。

### 2.4 规则试运行（Dry Run）

| 模式 | 输入 | 输出 |
|---|---|---|
| 回放试运行 | 选择一个历史 Run | 在它的 observation 序列上离线执行 oracle 规则，列出会命中的步骤和截图 |
| 静态试运行 | 选择项目 + 分支 | 静态规则在当前代码上的 Finding 列表 |
| 注入预览 | 选择项目 + 阶段 + URL | 展示 RuleResolver 最终会注入的规则、顺序、token 占用和被截断的条目 |
| 在线试运行 | 选择项目 + URL（test 模式） | 启动一个只读 Run，只执行探索和规则检查，不修复 |

### 2.5 规则集

- 规则集是规则的有序集合，例如「电商结账基线」「无障碍 AA 基础」「控制台零报错」。
- 可以绑定到项目，作为默认规则集；Job 可以额外追加规则集。
- 支持继承：项目规则集 = 组织基线 + 项目增量；可以覆盖单条规则的严重级别或停用某条规则（覆盖本身也保存为版本化记录）。

### 2.6 命中与质量看板

| 指标 | 计算 | 用途 |
|---|---|---|
| 命中数 | 规则产生的 Finding 数 | 了解活跃度 |
| 复现率 | reproduced / suspected | 判断规则是否可靠 |
| 误报率 | false_positive / 总数（来自人工标注） | 下线或修订规则 |
| 修复率 | fixed / reproduced | 衡量修复能力 |
| 注入但未引用率 | 已注入、但模型输出中没有引用 | 引导规则写法是否有效 |
| token 占用 | 平均每次注入的 token 数 | 精简规则写法，减少上下文窗口占用 |

### 2.7 权限

| 角色 | 规则权限 |
|---|---|
| 组织管理员 | 管理组织级规则 / 规则集，发布 Skill，查看审计 |
| 项目维护者 | 管理项目级规则，把规则集绑定到项目 |
| 成员 | 查看、试运行，创建草稿，提交发布申请 |
| 只读 | 查看 |

组织级规则发布需要审批（双人复核，可配置）。所有变更写入审计日志：操作人、时间、前后差异、来源 IP。

### 2.8 API（REST，前缀 `/api/v1`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/rules?scope=&category=&status=&q=&page=` | 列表 |
| POST | `/rules` | 新建（草稿） |
| GET | `/rules/{id}` | 当前版本 |
| PUT | `/rules/{id}` | 保存新版本（`If-Match: version`，乐观锁） |
| POST | `/rules/{id}:publish` / `:disable` / `:archive` | 状态变更 |
| DELETE | `/rules/{id}` | 只允许删除从未被引用过的规则 |
| GET | `/rules/{id}/versions`、`/rules/{id}/versions/{v}` | 版本历史 |
| POST | `/rules/{id}:rollback` | 回滚：以指定版本内容创建一个新版本 |
| POST | `/rules/{id}:test` | 试运行，返回 task id，结果通过 SSE 推送 |
| POST | `/rules:import`、GET `/rules:export` | 批量导入导出 |
| GET/POST/PUT | `/rule-sets`、`/rule-sets/{id}` | 规则集 |
| PUT | `/projects/{id}/rule-sets` | 绑定项目 |
| GET | `/rules/insights?from=&to=` | 质量指标 |

当前 Demo 的可用路径使用 `/api` 前缀（生产控制面仍规划为 `/api/v1`）：

| 方法 | 路径 | 已实现行为 |
|---|---|---|
| GET/POST | `/api/rules` | 按项目、状态、关键字列表；创建草稿 |
| GET/PUT/DELETE | `/api/rules/{id}` | 查看、保存新版本、删除未被引用规则 |
| POST | `/api/rules/{id}:publish` / `:disable` / `:archive` | 乐观锁状态变更 |
| GET | `/api/rules/{id}/versions` | 版本历史 |
| POST | `/api/rules/{id}:rollback` | 从历史版本创建新版本 |
| GET | `/api/rules/{id}/findings` | 查询命中记录 |
| GET | `/api/rules/insights` | 复现率、误报率、修复率 |
| GET/POST | `/api/rule-sets` | 规则集基础记录 |
| POST | `/api/runs/{id}/derive` | 创建派生 Run；请求体可传 `additionalRuleIds`，父 Run 规则快照自动继承 |

CLI 对应命令见 `08-交互设计/命令行CLI.md` 中的 `tracefix rules`。

### 2.9 存储（Postgres）

```sql
CREATE TABLE rules (
  id TEXT PRIMARY KEY, org_id TEXT NOT NULL, scope_level TEXT NOT NULL,
  current_version INT NOT NULL, status TEXT NOT NULL, owner TEXT,
  created_at TIMESTAMPTZ, updated_at TIMESTAMPTZ);
CREATE TABLE rule_versions (
  rule_id TEXT REFERENCES rules(id), version INT, body JSONB NOT NULL,
  body_hash TEXT NOT NULL, change_note TEXT, author TEXT, created_at TIMESTAMPTZ,
  PRIMARY KEY (rule_id, version));
CREATE TABLE rule_sets (id TEXT PRIMARY KEY, org_id TEXT, name TEXT, parent_id TEXT, version INT);
CREATE TABLE rule_set_items (set_id TEXT, rule_id TEXT, override JSONB, ord INT,
  PRIMARY KEY (set_id, rule_id));
CREATE TABLE project_rule_sets (project_id TEXT, set_id TEXT, PRIMARY KEY (project_id, set_id));
CREATE TABLE findings (id TEXT PRIMARY KEY, job_id TEXT, run_id TEXT, rule_id TEXT,
  rule_version INT, severity TEXT, status TEXT, fingerprint TEXT, data JSONB,
  created_at TIMESTAMPTZ);
CREATE INDEX findings_rule_idx ON findings(rule_id, created_at);
```

个人模式下使用同构的 SQLite 表。规则也可以放在仓库里作为「规则即代码」：`.tracefix/rules/*.yaml`，以项目级、只读的方式合并到规则集中（规则即代码导入尚未接入当前 Demo）。

## 3. 当前前台实现

页面入口为现有 BugBoard 的「检测规则」导航（`demo/bugboard/src/components/RulesPage.tsx`），不依赖新增前端工程。已交付：

1. 规则列表：关键字、状态筛选；展示类型、类别、严重级别、优先级、版本、命中数和误报率。
2. 规则编辑：规则 ID、名称、类型、类别、严重级别、优先级、置顶、JSON 检测配置、JSON 作用域、修复指引、标签和负责人。
3. 生命周期：保存新版本、发布、停用、归档、删除；已引用规则由后端拒绝物理删除；新建同名 ID 返回 409，不会覆盖旧规则。
4. 质量区块：显示当前规则版本历史和复现率、误报率、修复率；刷新时从后端重新读取。
5. Run 详情：展示冻结规则版本，支持选择新规则或草稿创建派生 Run；父版本不会被同名追加规则覆盖，父 Run 尚无快照时拒绝派生。

首次初始化本地 SQLite 时会自动显示 5 条内置演示规则：`builtin_console_no_error`、`builtin_api_no_5xx`、`builtin_submit_feedback`、`builtin_input_label`、`builtin_empty_state`。规则详情的「注入提示词预览」展示模型会收到的约束和可引用的 `rule_id`。

职责分工：React/TypeScript 实现页面与交互，`console-ts` 负责规则 CRUD、版本、初始化、校验、单规则预览和运行索引；Python 负责 Agent 执行、候选快照、动态适用性过滤、实际上下文注入和 Oracle/静态 Finding。规则不经过知识库的模型选择流程；每次请求仅注入运行时判定适用的完整规则，模型不得忽略。控制台与引擎必须使用同一 SQLite 路径。

尚未纳入本次前台代码的设计项：YAML 双向编辑器、历史快照点选 locator、离线回放/在线 Dry Run、组织审批与 RBAC、SSE 试运行进度、Finding 人工标注工作流。它们仍按本文件第 2 节的产品设计排期，不应被当前 Demo 页面误认为已交付。
