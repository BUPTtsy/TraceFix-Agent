# 前端工程化适配 📐

本文说明工程层（L2）如何读取元框架、构建工具、模块解析和 monorepo 的配置，为定位提供路由表、导入图和运行时叠加配置。UI 框架本身的写法见 `前端框架适配.md`。

## 1. 路由表

路由表把「当前页面 URL」和「失败的请求」对应到代码，是定位时收窄范围最有效的信号。前端页面路由和服务端接口路由都写入 UCM 的 `routes` 表，路径统一归一化为 `/tasks/:id` 的形式。

### 1.1 前端页面路由

| 框架 / 路由库 | 路由来源 | 规则要点 | 分期 |
|---|---|---|---|
| Next.js（App Router） | `app/**/page.*`；接口为 `app/**/route.*` | `[id]` 动态段、`[...slug]` 捕获段、`(group)` 路由组不进入 URL、`@slot` 并行路由；`layout` 参与组成渲染树 | P0 |
| Next.js（Pages Router） | `pages/**`；接口为 `pages/api/**` | `index` 对应目录路径 | P0 |
| Nuxt 3 | `pages/**/*.vue`；接口为 `server/api/**`、`server/routes/**` | `[id]`、`[...slug]`；`layouts/` 与 `app.vue` 参与组成渲染树；接口文件名后缀表示 HTTP 方法（如 `[id].patch.ts`） | P0 |
| vue-router | `createRouter({ routes })`（Vue 3）/ `new VueRouter({ routes })`（Vue 2） | 嵌套 `children`、懒加载 `() => import()`、命名路由、`redirect` / `alias` | P0 |
| React Router（库模式） | `createBrowserRouter([...])`、`<Route path element>` | 嵌套路由、`index` 路由 | P0 |
| 原生多页面 | HTML 文件路径即 URL（按开发服务器或构建配置的根目录） | hash 路由需要读取应用自己的分发代码，只能做到 L2 近似 | P0 |
| SvelteKit | `src/routes/**/+page.svelte`、`+layout.svelte`；接口为 `+server.ts` | `[id]`、`[[optional]]`、`[...rest]`、`(group)`；`+page.ts` / `+page.server.ts` 中的 load | P1 |
| Angular Router | `Routes` 数组（`provideRouter` / `RouterModule.forRoot`） | `loadComponent` / `loadChildren` 懒加载 | P1 |
| Remix / React Router 7 | `app/routes/**`（扁平命名：`.` 分隔路径段，`$id` 表示动态段），或 `app/routes.ts` 配置 | loader / action 是数据入口 | P2 |
| Astro | `src/pages/**` | `[id]`、`[...slug]` | P2 |
| UmiJS | 约定式的 `src/pages/**`，或 `.umirc.ts` / `config/config.ts` 中的 `routes` 配置 | 有配置时以配置为准 | P2 |
| 跨端框架的 H5 产物（uni-app、Taro） | `pages.json` / `app.config.*` | 源码标签与 DOM 标签不同名，需要标签映射表，接入时按版本核实 | P2 |

### 1.2 服务端接口路由

| 写法 | 示例 | 分期 |
|---|---|---|
| Express / Koa / Fastify / Hono | `app.patch('/api/tasks/:id', h)`、`router.route(p).get(h)`、`fastify.route({method, url})`；`app.use('/api', router)` 的前缀要叠加 | P0 |
| NestJS | `@Controller('tasks')` + `@Patch(':id')` | P0 |
| 元框架的文件接口 | Next `route.ts`、Nuxt `server/api`、SvelteKit `+server.ts` | 随 1.1 节 |
| **手写路由** | 在 `node:http` 回调中比较 `url.pathname` 和 `req.method`，或用正则匹配路径 | P0 |
| 其他语言 | FastAPI / Flask 装饰器、Django `urls.py`、Spring `@GetMapping`、Go `http.HandleFunc` / gin | P2 |

演示项目用的就是手写路由（`bugboard/target/server/index.mjs:25-36`）：

- `url.pathname === '/api/tasks' && req.method === 'GET'` 这类字符串比较；
- `url.pathname.match(/^\/api\/tasks\/(\d+)$/)` 之后再分支判断 `req.method === 'PATCH'`。

因此 P0 必须支持两类抽取：从「路径比较 + 方法比较」的条件中抽取路由；把正则路径转成模式，例如 `^\/api\/tasks\/(\d+)$` 转成 `/api/tasks/:p1`。这类路由记为 `source=code`，置信度低于框架式路由。

### 1.3 抽取规则

- **静态优先**：配置式路由从 AST 中读取字面量。路由表由循环、函数或远程数据动态生成时，退回按目录和命名约定近似匹配，并在 `files.level` 中记为 L1。
- **渲染树**：页面组件、布局和嵌套路由组成渲染子树，供定位时收窄范围（`GUI到代码定位.md` 第 4 节）。
- **懒加载**：`() => import('./views/Board.vue')` 记为 `route_to` 关系，指向目标文件。

## 2. 构建工具与叠加配置

「定位构建」需要开启 source map 并加入插桩插件（`GUI到代码定位.md` 7.2 节），但不能修改工作区里的任何文件，所以统一采用「叠加配置」的方式。

| 构建工具 | 需要读取的配置 | 叠加方式 | 分期 |
|---|---|---|---|
| Vite | `resolve.alias`、`resolve.extensions`、`server.proxy`、`base`、`css.devSourcemap`、插件列表、`envPrefix` | 用 `vite --config <overlay>` 启动；overlay 通过 `mergeConfig` 合并项目配置，再追加插桩插件，并开启 `css.devSourcemap` | P0 |
| webpack | `resolve.alias`、`devServer.proxy`、`devtool` | overlay 包装项目配置，追加 loader，并设置 `devtool` 为 source map | P0 |
| Vue CLI（维护模式） | `vue.config.js` 中的 `configureWebpack` / `chainWebpack` | 同 webpack | P0 |
| Create React App（已停止维护） | react-scripts 内置配置 | 不插桩，只用开发模式默认开启的 source map 和静态定位 | P0 |
| Nuxt / SvelteKit / Astro | 各自的配置文件（底层是 Vite） | 通过 Vite 插件注入 | P0（Nuxt）/ P1 / P2 |
| Next.js | `next.config.*`（底层是 webpack 或 Turbopack） | webpack 模式下通过 webpack 配置注入；Turbopack 下的注入方式待核实 | P1 |
| Rspack / Rsbuild | 与 webpack 兼容 | 同 webpack | P1 |
| Angular CLI | `angular.json` 中的 `sourceMap`、`fileReplacements`、`proxyConfig` | 官方构建管线不开放插件；只用 source map 和 `ng.*` 调试 API，不做模板插桩 | P1 |
| esbuild / Rollup / Parcel | 构建脚本 | 优先用 source map；插桩按需适配 | P2 |
| 自定义启动脚本 | Profile 中的启动命令 | Profile 另外声明「定位启动命令」 | P0 |

以演示项目为例：`scripts/dev.mjs` 同时启动 `server/index.mjs` 和 `node_modules/vite/bin/vite.js`。它的「定位启动命令」要分别启动这两者，并给 Vite 加上 `--config <overlay>`。

**约束**：

1. **不进入补丁**：overlay 文件放在工作区之外（`<run_dir>/overlay/`），不进入 `source_manifest`，也不会出现在补丁里。
2. **只用于定位回放**：REPRODUCE 和 VERIFY 使用与基线一致的非插桩构建。两种构建的 `environment_digest` 不同，插桩构建产出的证据不能进入验证门禁。
3. **需要审计**：「定位启动命令」属于已审计命令的变体，在确认 Profile 时一并审计。
4. **可以关闭，失败时降级**：Profile 中设 `code_intel.instrumentation: auto | off`。叠加构建启动失败时，降级为静态定位，并发出 `code_intel.degraded` 事件，Run 照常继续。

## 3. 模块解析

导入图的准确性决定了跨文件定位的质量。解析顺序与项目自身的配置保持一致：

- **tsconfig / jsconfig**：`baseUrl`、`paths`，包括 `extends` 链与 project references。
- **构建工具别名**：Vite / webpack 的 `resolve.alias`。从配置文件的 AST 中读取字面量；非字面量配置降级为按 tsconfig 和目录约定近似解析，并记录原因。
- **包入口**：`package.json` 的 `exports` / `imports`（如 `#internal`）、`main` / `module`、条件导出。
- **扩展名与目录索引**：`.ts` `.tsx` `.js` `.jsx` `.mjs` `.vue` `.svelte` 和 `index.*`，顺序与项目配置一致（如 Vite 的 `resolve.extensions`）。
- **样式导入**：`@import`、`@use`、`~` 前缀；CSS Modules 的 `import styles from './x.module.css'`。
- **资源导入**：`import url from './a.svg'`、`new URL('./a.png', import.meta.url)`。
- **以 LSP 为准**：L3 可用时以 LSP 的解析结果为准，上述静态解析是 L2 兜底。
- **配置文件只读不执行**：`vite.config.ts` 等配置文件本身是代码，只做静态读取，绝不在宿主执行。必须执行才能得到的值，在沙箱内用 Profile 审计过的命令获取，否则降级。

## 4. monorepo 与包管理

- **识别**：`pnpm-workspace.yaml`、`package.json` 的 `workspaces`（npm / yarn / bun）、`nx.json`、`turbo.json`、`lerna.json`、`rush.json`。
- **按包探测**：每个包单独探测框架与构建工具。
- **跨包导入**：指向工作区内的源码，而不是 `dist`。通过包的 `exports` / `source` 字段或 tsconfig references 解析。
- **索引范围**：Profile 指明被测应用所在的包（如 `apps/web`），索引覆盖该包及其在工作区内的依赖。
- **版本**：包管理器由 lockfile 判断（`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`、`bun.lock` / `bun.lockb`），实际安装的版本用于判断框架版本。

## 5. 自动导入与约定

模板里直接使用、却没有 import 的组件和函数，要靠以下机制解析：

| 机制 | 解析方式 |
|---|---|
| unplugin-vue-components / unplugin-auto-import | 读取生成的 `components.d.ts` / `auto-imports.d.ts`（读取但不索引）。文件缺失时，按插件配置中的目录和 resolver（如 `ElementPlusResolver`）推断 |
| Nuxt 的组件与组合式函数 | 读取 `.nuxt/components.d.ts`、`.nuxt/imports.d.ts`，需要沙箱中执行过 `nuxi prepare` 或启动过 dev。文件缺失时按目录约定推断，例如 `components/base/Button.vue` 对应 `<BaseButton>` |
| Vue 全局注册 | `app.component('Name', Comp)`；`app.use(plugin)` 中注册的组件按组件库角色表处理 |
| Angular | standalone 组件的 `imports`，或 NgModule 的 `declarations` / `exports`，决定模板中哪些 selector 可用 |
| SvelteKit | `$lib` 等别名，来自 `svelte.config.js` 的 `kit.alias` 和生成的 `.svelte-kit/tsconfig.json` |
| 原生页面的全局脚本 | 按 `<script src>` 的加载顺序确定全局变量的可见性 |

## 6. 环境变量与开发代理

- **环境变量**：`import.meta.env.VITE_*`、`process.env.NEXT_PUBLIC_*`、`NUXT_PUBLIC_*` 等会影响请求的 base URL。静态解析时，只读取 `.env.example` 和 Profile 中声明为非敏感的键（如 `VITE_API_BASE`），不读取 `.env` 中的密钥。
- **开发代理**：Vite 的 `server.proxy`、webpack 的 `devServer.proxy`、Angular 的 `proxy.conf.json`。网络映射时，先按代理规则改写 URL，再与服务端路由匹配。

## 7. SSR、水合与岛架构

- **SSR**：Next、Nuxt、SvelteKit、Astro 中，同一个组件在服务端和客户端各执行一次。水合不匹配（hydration mismatch）的 console 警告作为一类专门的信号，定位到对应的组件和数据来源，如服务端 load、`getServerSideProps`、`useAsyncData`。
- **服务端日志**：服务端报错的堆栈在开发服务器的进程日志里（沙箱内），需要把应用日志纳入观测，日志来源由 Profile 声明。
- **岛架构**：Astro 中只有 `client:*` 岛内的组件有客户端事件，岛外都是静态 HTML，定位交互类缺陷时只查岛内。
