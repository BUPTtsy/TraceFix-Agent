# 平台调用 Agent 的端到端流程

> 定位更新：2026-10-07。交互主体为程序调用方与 TraceFix Agent 组件；Web / CLI 保留为研发入口。`/api/v1/tasks` 已区分 Task 定义与 Run 执行；稳定 result、请求幂等和统一仓库注册 API 仍按接口型 Beta 计划补齐。

## 1. 职责与输入

| 参与方 | 职责 |
|---|---|
| 程序调用方 | 提供仓库、规则、目标及执行信息，创建 / 编辑 / 启动 / 停止 Task，查询 Run 与消费结果 |
| TraceFix 接口层 | 按仓库管理配置、规则、Task / Run；校验输入与生命周期，返回状态和产物 |
| Agent 运行时 | 冻结规范、浏览器检测与复现、源码定位、最小修补、独立验证和审计 |

组件不感知或判断用户身份、角色和权限，也不要求调用平台建设用户管理。调用方提供仓库地址 / 凭据引用、受审 Profile、源码 revision、可重置测试环境、目标 / TestSpec 和规则版本；运行时校验这些执行资源，不把凭据或角色放进自然语言目标和模型上下文。

管理粒度为仓库，Task 定义与该仓库绑定，Run 记录每次执行。当前 Task、Run 索引、规则和知识等部分元数据保存在 SQLite，后续迁移至 MySQL；仓库注册仍由 YAML / JSON 与 Profile 提供，PostgreSQL 仍用于 Agent 执行状态、事件和 checkpoint。

## 2. Task 生命周期

1. 调用 `POST /api/v1/tasks` 提交仓库、模式、目标及受支持的执行信息，并固定 `executionMode=batch`；默认返回 `201` 与 `created`，尚未启动 Agent。首版不接受依赖审批的 interactive Task。
2. 调用 `POST /api/v1/tasks/:id/start` 单独启动，返回 `202`、Task 视图、`currentRunId` 与 Run 摘要；每次启动创建新 Run。执行配置应通过编辑 Task 更新，不在启动请求临时替换。
3. 创建时传 `create_and_start=true`，或使用 `POST /api/v1/tasks:create_and_start`，可合并创建与启动。若执行器忙，创建的 Task 保留，`409` 携带 `taskId` 和 `status_url`，可查询并稍后启动。
4. `PUT /api/v1/tasks/:id` 编辑任务；运行、暂停、等待输入 / 审批或正在停止等活动状态返回 `409`。停止或结束后编辑回到 `created`，再次启动从新 Run 重新开始，历史 Run 与证据保留。
5. `POST /api/v1/tasks/:id/stop` 仅停止该 Task 当前 Run；未启动或已结束保持幂等。当前 API 不能控制其未持有的活动进程时明确返回 `409`。

原 Run 的 `/api/runs/:id/continue` 续跑沿用原 Run、工作区和冻结规范，是旧 interactive / CLI 兼容功能；Task 编辑后启动不走该恢复路径。

## 3. 检测流程

1. 调用方选择仓库与运行配置，创建 `mode=test` 的 Task，并由独立接口启动或显式创建并启动。
2. Agent 为本次 Run 校验仓库与执行配置，冻结源码、规则、目标和测试规范。
3. Agent 执行 PREPARE → EXPLORE → REPRODUCE，记录动作、观测、规则覆盖和证据。
4. 调用方查询 Task 当前 Run，并通过现有 `/api/runs` 读取状态、事件与产物；权威 result 接口仍待补齐。
5. `BUG_CONFIRMED` 表示缺陷已确认；`NO_BUG_FOUND` 只表示充分覆盖的冻结范围无问题。未检查的必检规则不计为通过。

## 4. 指定缺陷修复流程

1. 调用方选择来源 Test Run 的 Finding，创建绑定来源、仓库、规则快照和约束的 Repair Task，再启动新 Run；完整来源契约仍待 B3 / B4 验收。
2. TraceFix 检查来源归属并重新复现；不能把别的仓库、Run 或不明来源证据作为当前修复依据。
3. Agent 执行 DIAGNOSE → PATCH → VERIFY，使用当前源码 hash 做局部编辑。
4. 验证原问题、逆向行为、刷新与正常业务，以及 static / unit / build / health。
5. 接口返回 outcome、diff、补丁验证状态和证据，由调用方审阅和消费结果。

`FIX_VERIFIED` 必须绑定当前补丁与有效验证；空 diff、未验证候选或退化补丁不能作为修复成功。历史 B01 自动报告曾被独立业务审查拒绝，该记录继续作为负例保留。

## 5. 中断、取消与干预

| 情况 | Agent / 接口行为 | 调用方处理 |
|---|---|---|
| 忙碌或输入未就绪 | 稳定错误，不伪造已启动 Run；创建并启动忙时保留 Task | 查询原 Task，等待就绪后单独启动 |
| 重复提交 | 请求幂等尚待 B4 完成，不能宣称相同请求自动去重 | 保存 Task / Run ID，避免无确认重复创建 |
| HTTP 断连 | 不因连接断开推断成功或失败 | 按已有 Task / Run 查询状态 |
| 指定 Task 停止 | 仅停止当前 Run，保留状态与产物；无法控制进程时明确拒绝 | 展示停止状态与拒绝原因 |
| 编辑活动任务 | `409`，不改变当前执行配置 | 先停止并确认终态，再编辑 / 启动新 Run |
| 无进展 / 过期观察 | 有界恢复或明确终态，保留证据 | 展示失败原因，按支持范围发起新任务 |
| 副作用结果 UNKNOWN | 保留核查要求，不盲目重放 | 核对外部状态后决定后续任务 |
| 改目标 | 现有 L3 Guidance 确认后派生 Run | 显式确认并保留父子来源，旧证据不等于新结论 |

暂停、继续、审批和引导只能采用实际已支持的状态语义，不承诺任意浏览器阶段透明恢复。接口首版不能无期限等待 TTY 或人工点击。

## 6. 结果消费与验收

调用方按 Task 与 Run 的状态、outcome、规则覆盖、Finding、patch、verification、error 和 provenance 组合展示结果。HTTP 2xx、`COMPLETED` 或进程退出码不能单独用作缺陷修复结论。

首版验收包含 Task 创建 / 启动 / 编辑 / 停止、新 Run 重启与历史保留、一个真实有效闭环、退化补丁拒绝、UNKNOWN、有界恢复、待补齐的幂等 / 指定 Run 取消和 A → B → A 两仓库隔离。既有 CLI 与 Web 仅做必要兼容性回归；通知、PR 评论和用户权限模型不进入组件交付范围。
