# 记忆与上下文压缩

## 1. 现状

### 1.1 上下文构建方式：类型化状态重建，不累积对话

每次模型调用都由 `build_context` 从 RunState 重新组装上下文，而不是把历史消息越堆越长（`knowledge/context.py:15-36`，注释「Typed state replaces raw histories」在第 24 行）。这是一个好的基础：上下文大小基本与 Run 的长度无关。

| 机制 | 实现 | 证据 |
|---|---|---|
| 受保护区块 | policy、test_spec、scope、phase、patch_hash、evidence_refs、goal | `context.py:19-22` |
| 历史窗口 | 最近 4 个「动作-结果」对 | `context.py:25`、`engine.py:401` |
| 去重 | 按 JSON 序列化结果去重 | `context.py:26-31` |
| 硬预算 | 65,000 **字符**，超出直接抛异常（不是自动压缩） | `context.py:15,34-35` |
| 观测截断 | snapshot 保留末尾 40,000 字符；console / network 各保留末尾 12,000 字符 | `execution/browser.py:330,333` |
| token 预算 | 按 UTF-8 字节估算，并预留 4096 | `engine.py:153-155`、`contracts.py:74` |
| 长期记忆 | Postgres `memory_items`：M1 代码事实、M3 修复经验，词法 + 向量检索，RRF 融合 | `storage/schema.sql:17-25`、`knowledge/retrieval.py` |
| 经验沉淀 | `/runs remember` 把运行结果归档为经验 | `cli/workspace.py:322-377` |
| Chat 历史 | 内存字典，最多 20 轮，进程重启即丢失 | `cli/main.py:411-412` |

### 1.2 局限

1. 用字符而不是 token 计算预算，中英文混排时误差很大；超预算时直接报错，没有降级策略。
2. snapshot 从尾部截断，页面顶部的关键区域会丢失。
3. 历史只保留最后 4 步，更早的探索经验（哪些路走不通）完全丢失，容易重复犯错；目前只靠 `repeated_action` 兜底（`engine.py:48-49`）。
4. 没有 Run 内的工作记忆（假设、已排除的方向、待办）。`hypothesis_refs` 字段存在（`contracts.py:214`），但只保存补丁方案。
5. 没有跨 Run、Job 级的应用知识（页面地图、登录流程、易抖动的元素）。
6. 长期记忆依赖 Postgres；没有 Postgres 时静默失效（`retrieval.py:61-63`）。
7. 上下文中缺少稳定的前缀结构，无法利用供应商的 prompt cache。

## 2. 目标设计 📐

### 2.1 分层记忆模型

| 层 | 名称 | 生命周期 | 内容 | 写入者 | 存储 |
|---|---|---|---|---|---|
| L0 | 工作上下文 | 单次模型调用 | 由上下文组装器按窗口分区拼出的区块 | 运行时 | 仅作为 request artifact 保存 |
| L1 | Run 工作记忆 | 单个 Run | 假设及置信度、已排除项、关键发现、待办、进展摘要 | 模型（`memory.note`）+ 运行时模板 | RunState + artifact |
| L2 | Job 记忆 | 单个 Job | 应用地图（路由、页面、导航路径）、登录流程、抖动元素、公共前置步骤 | DISCOVER 阶段、各 Run 汇总 | Job 记录 |
| L3 | 项目长期记忆 | 跨 Job | M1 代码事实、M3 修复经验、应用知识；带来源和有效期 | 经审核后晋升 | Postgres / SQLite |
| L4 | 组织知识 | 长期 | 检测规则、知识文档、Skill | 管理员 | 控制面 |

晋升规则：L1/L2 → L3 需满足「Run 结果为 `FIX_VERIFIED` 且经人工确认」，或由维护者手动标记；每条记忆都要记录 `source_run_id` 和 `source_manifest`。代码变更导致 `source_manifest` 失配时，记忆降权或标记失效（沿用现有 `source_revision` 字段，`schema.sql:20`）。

### 2.2 上下文组装器（Context Assembler）

把现有的 `build_context` 升级为「窗口分区」模型，**区块按稳定度从高到低排列**，以便命中 prompt cache。下表的占比是单次请求内对模型上下文窗口的空间分配，不是运行预算：超出时只压缩或裁剪，不会结束 Run。

| 顺序 | 区块 | 窗口占比 | 可压缩 | 说明 |
|---|---|---|---|---|
| 1 | `policy` | 固定 | 否 | 系统安全策略 |
| 2 | `project_instructions` | ≤5% | 否（超限拒绝） | AGENTS.md |
| 3 | `detection_rules` | ≤15% | 置顶规则不压缩，其余降级为摘要 | 见 `04-检测规则/规则模型与注入.md` |
| 4 | `skills` | ≤8% | 按需加载 | 见 `03-Agent运行时/工具调用与Skill.md` |
| 5 | `task`（goal + test_spec + brief 约束） | 固定 | 否 | 冻结内容 |
| 6 | `user_guidance` / `review_guidance` | ≤5% | 否（过期条目移除） | 见 `03-Agent运行时/用户提示词干预.md`；修订 Run 中的 `review_guidance` 见 `03-Agent运行时/PR评审意见驱动修复.md` |
| 7 | `working_memory`（L1 摘要） | ≤10% | 是（再压缩） | — |
| 8 | `job_memory` / `retrieved_memory`（L2/L3） | ≤8% | 是（按相关度截断） | — |
| 9 | `code_insights` | ≤25% | 是（按置信度截断） | 见 `05-代码分析/AST分析与动态注入.md` |
| 10 | `observation`（压缩后的快照 + 截图） | ≤20% | 是（树裁剪 / 差分） | 见 `03-Agent运行时/浏览器MCP接入.md` 2.3 节 |
| 11 | `recent_steps`（滑动窗口） | 剩余部分 | 是（滚动进入摘要） | — |
| 12 | `instruction` | 固定 | 否 | 本阶段任务说明 |

- **计数**：使用供应商对应的 tokenizer（或 `tiktoken` 近似）按 token 计数，替换现有的字符计数。
- **超出窗口时的降级顺序**：recent_steps → observation 差分化 → code_insights 截断 → retrieved_memory 截断 → working_memory 再压缩 → 规则降级为摘要。受保护区块（1、2、5、6、12）不压缩；它们本身就超出窗口时（例如用户引导过长），Run 转入 PAUSED，提示用户精简内容，不结束 Run。
- **记录**：每次组装都生成 `context_manifest`（各区块的 token 数、哈希、被裁剪的条目 id），写入轨迹，训练时可以按区块还原。

### 2.3 会话压缩（Compaction）

| 触发条件 | 动作 |
|---|---|
| 滑动窗口外积累的步骤 ≥ 8 | 把旧步骤合并进「进展摘要」 |
| 组装后 token 占用 > 模型窗口的 70% | 强制 compact |
| 进入新阶段（EXPLORE→REPRODUCE、DIAGNOSE→PATCH） | 生成阶段小结，上一阶段的明细移出上下文 |
| 用户执行 `/compact` | 手动触发 |

压缩策略按「确定性优先」逐级使用：

1. **结构化摘要**（无模型）：步骤序列 → 模板化文本，例如「第 3-9 步：导航 /cart → 点击『+』×3 → 数量显示 3，符合预期」。
2. **失败要点保留**：导致断言失败、策略拒绝或工具错误的步骤原样保留（它们是后续推理的关键）。
3. **模型摘要**（兜底）：只有前两步之后仍超出窗口时，才调用廉价模型生成摘要。要求输出结构化字段（已确认事实 / 已排除假设 / 未决问题），并且每条都带 `evidence_refs`，不能凭空生成。

每次压缩发出 `context.compacted` 事件，内容包括：被合并的 step 范围、摘要 artifact、压缩前后的 token 数。轨迹导出时，压缩边界本身也作为一条训练信号（教会模型在长任务中依赖摘要）。

### 2.4 Chat 模式

- 历史持久化到存储（个人模式用 SQLite，团队模式用 Postgres），按 `(user, project)` 分会话。
- 超过 20 轮后，更早的轮次合并为摘要，不再简单截断。
- CLI（`model/chat.py`）与 Web（`backend/apps/console-api/server/index.mjs:128-154`）目前是两套实现，统一收敛到后端的同一个 Chat 服务。

### 2.5 长期记忆的可用性

- 个人模式：用 SQLite FTS5 做词法检索，向量检索可选（本地 embedding 模型或关闭）。不再依赖 Postgres 才能使用记忆。
- 发生降级时发出 `memory.degraded` 事件，并在 CLI 的 `/memory`、Web 的运行详情中显示「记忆检索未启用」。

### 2.6 Prompt Cache

- 区块 1-5 在同一个 Run 内基本不变，作为稳定前缀。
- 公司内部模型服务（如 vLLM / SGLang）通常支持自动前缀缓存，稳定前缀即可命中；是否开启需在 M0 向模型平台团队确认。
- 网关记录 `cached_tokens`，写入 usage，用于用量统计。

### 2.7 验收指标

| 指标 | 目标 |
|---|---|
| 因上下文超出窗口而结束的 Run | 0（现状：超过 6.5 万字符即抛异常） |
| 30 步以上长流程场景的重复无效动作率 | 比基线下降 50% |
| 单次模型调用的平均输入 token | 比基线下降 30%（观测差分 + 窗口分区） |
| prompt cache 命中率（同一 Run 内） | ≥ 60% |
